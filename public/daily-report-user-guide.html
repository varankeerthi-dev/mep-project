01

The two modules

Tasks are the source of truth for what needs to get done. Daily reports are the source of truth for what actually got done. The two are linked through work items.

Tasks
planned work, lives in the project
→
Work items
the bridge — one per row
→
Daily reports
one per project, per day

Tasks

The list of work units for a project. Each task has a status, a progress percentage, a discipline, and an assignee. Tasks are planned ahead and live in the project for the duration of the work.

Daily reports

One per project, per day. Each report has rows of work items describing what happened. A report is the daily log the project manager and the client will read.

Work items

Each row in a daily report. A work item either references a task (planned work touched today) or is ad‑hoc (a snag, a delivery, a discovery). Progress, status, photos, notes, and blockers all live on the work item.

The rule of thumb

If you knew about it yesterday, it’s a task. If it surprised you this morning, it’s an ad‑hoc work item.

02

Your daily workflow

Most engineers spend five minutes at the start of the day and another five at the end. Here’s the rhythm.

Morning — plan the day

  1. Open today’s daily report for your project.
  2. Glance at any open work items still on the list.
  3. Add new work items for today. For each, decide: linked to a task, or ad‑hoc?
  4. If linked, pick the task from the typeahead. If ad‑hoc, type a short title and pick a discipline.

During the day — log as you go

  1. Tap a work item’s status cell when the work starts.
  2. Drag photos in as you take them. They auto‑attach to the work item you’re focused on.
  3. Update progress (0% → 100%) as work advances. The cell is inline — no modal.
  4. Flag a blocker the moment you hit one. Don’t sit on it.

End of day — close the loop

  1. For each work item, set progress_after to where you actually ended up.
  2. Add a one‑line note on anything that needs explaining.
  3. Submit the report. A confirmation toast appears — that’s it.
Auto‑save is on

Your report saves to your browser every 1.5 seconds. Close the tab, lose signal, spill coffee on your laptop — your draft is safe for 24 hours. When you come back, a Restore draft? banner offers to put everything back.

03

Tasks

Tasks live in the project. They have a status, a progress, a discipline, and a quantity. They are referenced — never duplicated — in daily reports.

Status lifecycle

not_started
Created, not yet started.
in_progress
Active work happening today.
blocked
Cannot proceed. Reason required.
done
Complete. Progress at 100%.

Progress

0% to 100%. A work item records the progress before and after it was touched. The task’s progress is the latest progress_after from any work item on it.

Discipline

Each task belongs to a discipline (electrical, mechanical, plumbing, and so on). A work item’s discipline is inherited from the task — unless the item is ad‑hoc, in which case you pick it yourself.

04

Work items

A work item is a row in a daily report. Each one carries the day’s work for a specific task — or for an unplanned piece of work.

What a work item holds

  • Task reference — null for ad‑hoc items, otherwise the task id.
  • Title — task title for linked items, free text for ad‑hoc.
  • Status — before and after, captured as a delta.
  • Progress — before and after, captured as a delta.
  • Quantity — a number and a unit (e.g. 50 m of conduit).
  • Photos — drag, drop, or paste. Multi‑file.
  • Blocker — a flag and a one‑line reason.
  • Note — anything else worth saying.

Linked vs. ad‑hoc

Linked items roll up to a task automatically. Ad‑hoc items exist only in the report they were created in — they don’t get pulled into the project’s task list. Use ad‑hoc for snags, deliveries, and discoveries.

Duplicate detection

If you try to add a work item that matches a recent ad‑hoc item (same title, same discipline), you’ll get a warning. Most of the time, the right move is to link the original — not create a new ad‑hoc.

05

Photos

Photos attach to work items. The drop zone accepts drag‑and‑drop, paste from clipboard, and click‑to‑browse.

Upload flow

  1. Drop or paste. A thumbnail appears immediately — it’s local‑first.
  2. The upload runs in the background through the photo RPC.
  3. If you lose connection mid‑upload, the queue persists in localStorage. It replays on reconnect.
  4. Once uploaded, the photo gets a server‑side id and is locked in.

Photo states

queued
On your device, waiting for upload.
uploading
In flight to the server.
uploaded
Persisted with a server id.
failed
Will retry on next reconnect.
Heads‑up on size

Each photo is compressed before upload. If you need full‑resolution originals, take them on your phone’s camera — the daily‑report photos are for evidence, not marketing.

06

Offline & drafts

The work doesn’t stop when the wifi does. The daily‑report form has a local‑first auto‑save that runs in the background.

How auto‑save works

  • Every 1.5 seconds of inactivity, the current draft is written to localStorage.
  • The draft expires after 24 hours.
  • On your next visit, if a draft is found, you get a Restore draft? banner.

Conflicts

If the server has newer data than your local draft (someone else edited, or you edited from another device), you’ll see a Conflict warning in the banner. The default is to keep the server’s version. Open the draft to copy‑paste any work you want to preserve.

Draft metadata

Storage key
site-report-draft:{projectId}:{date}:{userId}
Debounce
1.5 seconds
TTL
24 hours
Storage
localStorage (per browser, per device)
07

Weekly rollup

Once a week, the project manager opens the rollup. It aggregates the last seven daily reports into a single page with totals, blockers, and a PDF export.

What’s in the rollup

  • Tasks touched this week, grouped by discipline.
  • Progress deltas — what was 0% on Monday, what’s 100% on Sunday.
  • Blockers raised, with reasons.
  • Photos of the week, in order.
  • Quantity totals (e.g. 320 m of conduit installed).

Where to find it

The rollup lives at /projects/<projectId>/reports/rollup. The project overview page has a link to it under the Reports section.

PDF export

The rollup has a Download PDF button. It uses the same template the client sees, so what you see is what they get. Send it without reformatting.

08

Keyboard navigation

The work‑items grid is fully keyboard‑navigable. If you live in spreadsheets, you’ll be at home here.

← → ↑ ↓
Move the active cell left, right, up, or down.
Home End
Jump to the first or last cell in the current row.
Enter Space
Activate the cell — opens the inline editor or the typeahead.
Esc
Cancel the current edit. Value reverts to before the edit.
Tab
Leave the grid. Continues to the next focusable element on the page (e.g. the Add row button).

Focus is shown with a 2‑px Executive Blue ring. If you can’t see it, check your browser’s focus indicators setting — it should be on.

09

Roles & permissions

Not everyone sees the same thing. Permissions are enforced at the database level, not just the UI.

Field engineer
Creates and edits daily reports for projects they’re assigned to. Cannot edit reports from other engineers.
Project manager
Reads all reports for their projects. Reads the rollup. Can lock a section of a report to prevent late edits.
Quantity surveyor
Reads all reports + rollups. PDF export is in the default toolbar.
Admin
All of the above, plus the ability to force‑unlock, delete, and reassign.

Section locks

Once a project manager has reviewed a section of a report, they can lock it. A locked section shows a banner and prevents edits — even from the original author. The PM unlocks it explicitly when changes are needed.

The lock is a commitment

Locking a section signals “this is final.” Clients may have already been sent the report. If you need to change a locked section, talk to the PM first — they’ll unlock, you’ll edit, they’ll re‑lock and re‑send.
