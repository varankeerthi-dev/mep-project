# MEP performance audit: app shell and requested route groups

Dashboard and Operations have the largest source-derived cold-read fan-outs. Follow-up Centre runs eight data hooks before tab selection, while WarehouseModule mounts hidden sibling pages. Several lists and project-detail paths fetch broad result sets before local processing. These are source risks, not measured slowdowns.

The counts below are inferred query or API invocations, not observed network counts. No app API was called, no authentication was performed, and no business-data response or record was read. **Scope caveat:** public static app HTML, JavaScript, and source-map payloads were inspected for deployment correlation. Under a literal reading, these are response payloads; no further deployment fetches were made after this was recognized.

The workspace is at HEAD `1533b47dfb12e858b1b33fc6fffe41da77c12b1c` and has pre-existing uncommitted changes, including `apps/web/src/features/settings-v2/SettingsV2Page.tsx`, which affects the approval-settings wrapper. No source file was changed for this audit. **Exact** means deployed source content was compared with workspace source. **Partial** means a deployed route, chunk, symbol, or map was visible without exact parity. **Not confirmed** means the route chunk could not be mapped reliably. The two query-client files have different defaults, so the active provider must be confirmed before applying cache defaults globally (`apps/web/src/queryClient.ts:129-145`; `apps/web/src/config/queryClient.ts:3-14`).

## Suspected performance issues

Every finding below names the route, source evidence, deployment/workspace confidence, likely user impact, and a browser measurement that can prove or falsify it. No timing claim is made from static source.

### 1. Shared shell work and eager entry code

- **Route/tab:** Every authenticated route; `/store/materials/items/new` code is reachable globally.
- **Source:** `apps/web/src/App.tsx:23,43-84,840-843,940-975,1156-1181`; `components/Sidebar.tsx:517-529`; `hooks/useOrgModules.ts:13-47`; `components/QuickAccessBar.tsx:30-54`.
- **Evidence:** App statically imports ItemEditorPage and its deployed entry map includes its materials graph. The authenticated shell mounts org modules, permission, and QuickAccess queries; pending count polls every 30s. Auth/resume invalidation can refresh active queries, but a duplicate first-load wave is conditional on timing.
- **Deployed vs workspace:** App entry map includes App and the ItemEditor/materials symbols; exact parity for all shell child code is partial. Workspace has no matching source edits to App/Sidebar identified in the initial status.
- **Likely impact:** All authenticated users can pay extra JavaScript parse/compile cost, and shell requests/polling add work before or alongside route data.
- **Browser proof:** Cold authenticated trace with cache disabled. Record shell query initiators and timestamps, JS transfer/decode/evaluation, first content, and requests following auth/resume invalidation. Leave shell open for 60s to verify the pending-count interval.

### 2. Dashboard cold fan-out and broad reads

- **Route/tab:** `/` or `/dashboard` Home; Ledger; Dashboard refresh.
- **Source:** `apps/web/src/pages/Dashboard.tsx:80-96,139-164,222-229`; `hooks/useProjects.ts:9-22`; `hooks/useNextActions.ts:36-128,366-405,465-479`; `App.tsx:940-975`.
- **Evidence:** Home starts 16 query invocations. Several projects/claims/insights/action reads have no app-level limit. The profiles lookup lacks an organization predicate in the inspected source. Resume recovery invalidates active queries after startup; a second wave is a hypothesis, not a measured duplicate. Ledger adds two capped reads and realtime invalidations.
- **Deployed vs workspace:** Dashboard lazy chunk/map was observed; exact line parity with workspace is not confirmed. Workspace Dashboard source matches HEAD per area audit.
- **Likely impact:** Backend concurrency and client work begin before the Dashboard is stable; data volume can grow with organization history.
- **Browser proof:** Fresh authenticated `/dashboard` waterfall, count distinct query keys/URLs and row bytes; timestamp the auth-ready and recovery invalidation events; separately select Ledger and observe request delta and realtime refetches.

### 3. Operations repeated reads and eager dashboard zones

- **Route/tab:** `/operations` and `/operations-v2`.
- **Source:** `pages/operations/Operations.tsx:33-43`; `OperationsV2.tsx:80-95`; `api/useOperationsQueries.ts:21-428`; `api/useOperationsQueriesV2.ts:19-322`.
- **Evidence:** Legacy landing runs 16 query functions, about 15 network reads. `site_report_work_stoppages` is independently read by three queries, `site_visits` by two, and `quotation_header` by two. V2 runs 11 query functions and independently reads `site_visits` for Live Now and Upcoming Visits. Zones mount together; keys differ, so React Query deduplication is not assumed.
- **Deployed vs workspace:** Deployed HTML entry references both Operations chunks and route strings. Exact source-map parity is not confirmed.
- **Likely impact:** Redundant database reads and all-zone concurrency can lengthen the first useful dashboard render and increase backend load.
- **Browser proof:** Cold load each route with cache disabled; group requests by table/query key and initiator, count repeated table requests, and compare the request start/completion waterfall with zone visibility and route-ready paint.

### 4. Warehouse operations mounts hidden sibling pages

- **Route/tab:** `/warehouse/operations`, including Receiving, Transfers, Dispatch, Picking, Replenishment, Cycle Count.

## Cross-cutting patterns

- **Source-derived counts are not observed requests.** React Query may serve fresh cache entries; retry, auth, organisation ID, row presence, route state, and query `enabled` conditions can change network counts.
- **No single cache default can be assumed from file names alone.** Both `src/queryClient.ts` and `src/config/queryClient.ts` define clients with different GC/mount defaults. Confirm the provider imported by the running entry before attributing cache behavior.
- **Server pagination varies.** Confirmed examples include 20-row ProjectList ranges and cursor-paged collaboration messages. Several other lists use a hard cap or client-side page slice only. Backend row caps/RLS were not inspected.
- **Duplicate reads require distinct-key evidence.** Operations repeats reads against the same tables under distinct query keys. Approvals has one direct workflow call plus one query-hook call. Elsewhere, same-key deduplication depends on one QueryClient and was not assumed without source confirmation.
- **Lazy route chunks do not guarantee lazy tabs.** Leads and Subcontractors use coarse feature chunks. Follow-up hooks run before tab selection. WarehouseModule mounts hidden sibling pages. Operations dashboards mount all zones.
- **Realtime and polling affect repeat traffic.** QuickAccess pending count is 30s; Warehouse transfers is 30s; Ledger and Approvals have realtime invalidations; auth/resume can invalidate active queries.
- **Deployment parity is uneven.** Most areas have partial or unconfirmed route-chunk mapping. Public static asset names are not proof that workspace source is byte-identical. The workspace's uncommitted SettingsV2 wrapper change is particularly relevant to approval settings.
